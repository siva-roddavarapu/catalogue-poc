# DECISIONS

Every gap in the brief, what we chose, why, and how to change it later. Owner-approved decisions are marked as such. The full spec the build followed is [docs/SPEC.md](docs/SPEC.md).

## Stack choice and why

| Choice                                      | Why                                                                                                                                                                                | Alternative considered                                                                                                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **React 18 + Vite + React Router** (client) | The brief asks for one React client and one Node backend, and scores clear FE/BE boundaries. A static SPA keeps that line hard: the browser only ever talks to `/api`.             | **Next.js:** it blurs the boundary (server components and API routes in the same app) and its main benefits, SSR and SEO, aren't required. |
| **Fastify** (API)                           | Small, fast, good TypeScript types, a plugin model for helmet and rate limiting, and `app.inject()` for HTTP tests without opening a port.                                         | Express: older typings, and no built-in inject.                                                                                            |
| **Zod in `packages/shared`**                | One schema for the enquiry form, enforced in the browser (fast feedback) and on the server (authority). Product and error types are shared too, so the client and API can't drift. | Separate validation on each side: duplicated rules that drift.                                                                             |
| **npm workspaces**                          | One install, one lockfile, one `npm test`. No extra tooling (no Nx or Turborepo) for a three-package repo.                                                                         | —                                                                                                                                          |
| **tsx at runtime** (no API build step)      | One way to run TypeScript in dev, tests and the container. Nothing to keep in sync (S7).                                                                                           | A compiled `dist/`: listed as next-day work.                                                                                               |
| **Plain CSS Modules + `theme.css` tokens**  | "Look and feel will change": a re-theme is one file. No UI kit to fight or remove later.                                                                                           | Tailwind or a component library: more to learn, and harder to swap the look wholesale.                                                     |

## Architecture and boundaries

```
 Browser ──▶ /api (same origin: Vite proxy in dev, nginx in Docker)
                │
   routes/      HTTP only: Zod-validate params/query/body → call a service → reply. One error shape.
                │
   services/    CatalogueService (featured, category split, search, currency)
                EnquiryService   (re-fetch product, build email)
                │   depends on interfaces only
   ports/       ProductSource · MerchandisingProvider · EmailSender · Logger
                │   implemented by
   adapters/    FakeStoreProductSource | FixtureProductSource
                JsonFileMerchandising
                SmtpEmailSender (→ Mailpit) | InMemoryEmailSender (tests)

   container.ts the ONE place that picks adapters, from validated config
```

- **Boundaries are enforced, not just intended.** `FakeStoreProductSource.ts` is the only file that knows the Fake Store URL or response shape. A custom ESLint rule fails the build if `fakestoreapi.com` appears in any other source file. The upstream payload is validated with Zod at that boundary, so a shape change fails there, not in the UI.
- **Business rules live in services**, so they're tested without HTTP (`catalogue.service.test.ts`) and don't care where data comes from.
- **The web app has one network door**, `src/api/client.ts`. Screens get data through a small `useApi` hook that gives every view its loading, error (with retry) and empty states.
- **Tests use the real app with fake adapters.** `buildTestApp()` wires the real Fastify app to 8 hand-written products, in-memory curation and an in-memory outbox. Nothing touches the network.

## Assumptions

| A3  | A category with no curation       | `topRated` is `[]`. | A4  | Category identity in URLs         | URL-safe slug (`mens-clothing`) plus display name. That's accepted as what the AC literally asks for.                                                                                                                                     | Fake Store has no search endpoint. | A8  | What a product tile shows         | Image, title, formatted price. The whole tile links to `/product/:id`. The tile image has `alt=""` because the title is the next element, so a screen reader would otherwise read it twice. | A9  | Enquiry fields (AC5)              | name (2–100), email, phone (optional, 7–20 chars of digits/spaces/`+()-`), message (optional, ≤1000); `productId` comes from the URL, not a form field. ## Simplifications agreed before the build (owner-approved)

The aim is code the owner can defend line by line. Each cut is deliberate.

| #   | Spec said                             | We did                                                          | Why                                                                                                                                       |
| --- | ------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| S1  | MSW for web tests                     | `vi.mock` of `src/api/client.ts`                                | The client is the frontend's only network boundary, so mocking it there tests the same thing with one less tool.                          |
| S2  | Generic `lib/cache.ts`                | Timestamp and array inside the Fake Store adapter               | Only one thing is cached. A generic cache is speculative.                                                                                 |
| S3  | One retry on network error            | Timeout only                                                    | Fewer branches to test and explain. The fixture switch is the offline fallback.                                                           |
| S5  | CORS restricted to the web origin     | **No CORS plugin**                                              | The browser only calls same-origin `/api`, through the Vite proxy or nginx. Nothing is cross-origin, so a CORS rule would be dead config. |
| S6  | Honeypot field                        | Not built                                                       | The rate limit covers basic abuse for a PoC. Listed under "next day".                                                                     |
| S7  | (implicit) a compile step for the API | `tsx` runs the TypeScript directly, in dev and in the container | One runtime, no build output to keep in sync. A bundled `node dist/server.js` is a next-day item.                                         |

## Dropped (out of scope) and why

Pagination, sorting and filters, cart and checkout, auth, admin UI for curation (the JSON file is the admin), i18n, analytics, SSR/SEO, deployment and pipeline, enquiry persistence, customer confirmation email. No AC asks for them, and the time-box is 2–3 h.

## How this grows beyond the PoC

Each change below is a new adapter or config change behind an existing seam, not a rewrite.

| Change                                                        | What to do                                                                                                                                                                                                                                                                                  | What stays untouched                                                 |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **Swap the product data source** (a PIM, Shopify, a database) | Write `XProductSource implements ProductSource` (3 methods), map its shape to `SourceProduct`, and choose it in `container.ts` from a new `PRODUCT_SOURCE` value. `FixtureProductSource` already proves the switch.                                                                         | Services, routes, web app, tests (they use the fixture adapter).     |
| **Swap email to Amazon SES**                                  | `SesEmailSender implements EmailSender` using the AWS SDK `SendEmail`, chosen in `container.ts`. For resilience, put an SQS queue in front so a provider outage doesn't fail the request.                                                                                                   | `EnquiryService` and the email content.                              |
| **Swap the look and feel**                                    | Edit `apps/web/src/styles/theme.css` (colours, spacing, radii, fonts are all tokens). A deeper redesign changes CSS Modules per component; the data flow doesn't change.                                                                                                                    | API, data hooks, routes.                                             |
| **Persist enquiries / curation in a CMS**                     | Add an `EnquiryRepository` port (DynamoDB) and store before emailing; the returned UUID becomes the key. Replace `JsonFileMerchandising` with a CMS- or DynamoDB-backed `MerchandisingProvider` and give the owner an admin UI.                                                             | Curation rules (5 home picks, skip missing IDs) stay in the service. |
| **Deploy to AWS**                                             | API image → ECR → ECS Fargate or App Runner behind an ALB (adjust `trustProxy` to the ALB subnet). `vite build` output → S3 + CloudFront, routing `/api/*` to the ALB so the browser stays same-origin (no CORS needed). Env vars from SSM Parameter Store / Secrets Manager. IaC with CDK. | Application code.                                                    |
| **Scale out**                                                 | The API is stateless except the in-memory product cache and rate-limit counters. Move both to Redis/ElastiCache when running more than one task.                                                                                                                                            | Ports and services.                                                  |

## Next day of work

In priority order:

1. **Retry with backoff on the product source (S3).** During AC3 verification the first cold call to Fake Store hit the 5 s timeout and returned the designed 502. One retry would have hidden it.
2. **Security headers and a CSP for the web pages.** Helmet covers API responses only; the HTML is served by nginx or Vite, which set none.
3. **Honeypot field on the enquiry form (S6),** plus a CAPTCHA decision with the owner.
4. **Compiled API build (S7):** bundle to `dist/server.js` and run plain `node` in the container (smaller image, faster start).
5. **End-to-end test** (Playwright) for the AC1→AC5 click-through against `docker compose`, run in CI. Today that path is checked by hand (see the PR).
6. **Accessibility pass** with axe and a keyboard-only walkthrough; move focus to the "Thank you" heading after submit.
7. **Observability:** request IDs surfaced in error responses; metrics for upstream latency and email failures.
